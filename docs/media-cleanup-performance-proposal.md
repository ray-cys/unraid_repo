# Media Cleanup performance rewrite

Implemented in `media_cleanup.sh` v1.7.1. The daily schedule, action policies, retention, media paths and one grouped notification remain unchanged. The earlier observed run took about 573 seconds: Arr 513 seconds, SAB 52 seconds and quarantine 2 seconds. Production timing remains workload dependent; the first run builds reusable evidence.

1. **Measured phases.** Arr receipts/logs separate discovery, history, reconciliation, working state, durable publication and filesystem work, with entity/action counts, planning-read counts and sidecar capture/reuse counts. Nested timers overlap; adding them does not give elapsed wall time, especially with paired reads.
2. **Exact indexes.** Complete catalogues, episode/file IDs, history and queue ownership are indexed in job-owned RAM. Duplicate/ambiguous IDs fail validation. Queue pagination must have stable totals and unique IDs. Cached empty/partial/failed responses never establish absence. Native mutation read-back is uncached; verified responses receive fresh exact-ID indexes. Planning prefetches are invalidated before mutations.
3. **Pending work and rotating discovery.** Every eligible series still receives a fresh episode snapshot, and every movie a fresh catalogue observation. These checks continue to discover Plex deletions; a cached manifest cannot establish media presence. Settled sidecars may reuse their recorded manifest only when the policy, Arr file/episode IDs, monitoring state, folder identity/directory times and recorded-file metadata agree. Metadata read-back uses bounded stat batches to avoid a child process per sidecar. Pending deletion, folder cleanup or retirement bypasses reuse. A rotating 50-entity full inventory per application and seven-day maximum reuse age ensure full discovery continues. Changes and expired evidence may require additional captures within the existing runtime bound. In-flight edits invalidate reusable evidence. The pending-work index lives in the existing state JSON and is rebuilt from current observations.
4. **Batched observations.** Sonarr state is indexed once into per-series RAM shards. Planners and observation changes operate on that series, then merge once before the normal atomic app checkpoint. Missing/untouched series and unknown top-level state are preserved. History evidence is merged once per series instead of per episode. Radarr sidecar hints are accumulated and merged once. API/filesystem intents and their verified outcomes still publish immediately; no action journal is delayed for speed. An interrupted observation batch can be rebuilt from fresh evidence; durable intents still reconcile before new actions.
5. **Two bounded readers.** Independent Sonarr episode pairs and Radarr tag/catalogue discovery use at most two concurrent GET workers. Both workers finish or are cancelled/reaped before reconciliation or mutation. They share the 4,096 planning-read budget and synchronized failure circuit. The existing timeouts/retries remain; the cooperative deadline cancels incomplete prefetches and discards their data. Action-completion read-back is exempt from the planning budget so an issued change can finish verification. Modules and all mutations remain sequential.

Fresh quarantine hashes and before/after identity checks, Mover/mount guards, recovery holds, confirmation rules, retirement clocks, native recycling and immediate journals remain enforced. No Docker setting, additional cron entry or shared mutable cross-script cache is introduced.

Validation includes existing consolidated safety fixtures plus exact action/state parity against the pre-rewrite Sonarr workflow, shard merge/deletion preservation, stable/changed/rotating/racing sidecar evidence, duplicate-ID rejection, shared read limits, cancellation and failed-response rejection. Observe the new receipts over representative daily runs before making a production speed claim. The prior deployed script remains in the private deployment rollback directory.
