# Hubble script reliability

Scheduled, argument-free executions of the 18 live scripts are supervised by a small parent process. Graceful TERM/INT forwarding is registered before launch; existing producer traps complete before the parent records the final exit. The installed User Scripts Abort button also sends SIGKILL, which cannot run cleanup. Forced aborts and power loss therefore require interruption/journal reconciliation; this supervisor does not modify the plugin or claim forced-abort recovery. CLI commands and library sourcing keep their existing behaviour. Automatic production receipts accept only installed User Scripts paths; fixture/repository executions cannot contaminate live results. RAM and vault execution receipts are separate from producer results: `COMPLETED` means an invocation finished successfully, not that all media was decoded or all backup payloads restored. Overlapping invocations cannot overwrite the active receipt. No new cron entry is installed.

The existing hourly backup audit discovers enabled jobs through the shared User Scripts catalogue. It reports excessively long-running jobs without terminating them and checks completion against the actual cadence, with finish allowances for long jobs and an onboarding interval for new receipts. Missing/retired optional scripts drop out of active checks; history remains retained. Torrent execution findings remain console-only. Existing producer health, backup integrity and restore evidence checks remain independent.

Backup and Plex DBRepair notification failures retain exact subject, importance, summary and detail in a private outbox. The hourly audit retries at most three reports; the original producers also retain their lifecycle semantics. Retried ISS incidents record their exact request/reason acceptance so the existing daily reminder cooldown still applies. Successful delivery is acceptance by Unraid's notification helper, not proof of mailbox delivery. Other scripts retain their own grouped outboxes and daily/weekly limits. An unavailable vault uses a RAM spool; sudden power loss can lose that unpersisted spool. Routine healthy notifications are unchanged.

New appdata archives record GNU tar's already-streamed byte count rather than rewalking appdata. Legacy raw size zero means unknown. Oversized/unknown-size Plex archives receive a selective database/preferences restore; full-archive extraction remains bounded. The ISS default weekly drill is due once per Singapore calendar week during a normal backup session; custom non-weekly intervals retain elapsed-time checks. The coverage ledger explicitly distinguishes that selective test from a complete Plex Media restore. Extraction, hashes and database checks run in isolated staging and never overwrite live data.

The Arr monitor's global backup/update gate still prohibits pipeline actions. During deferral, bounded read-only Sonarr/Radarr ping and SAB version checks publish separate availability evidence, accounting for per-container maintenance. The DNS watchdog uses Pi-hole's own lease rather than suppressing primary checks during unrelated archives. No application setting is changed.

A native DBRepair intent is recorded before execution. Interrupted or unresolved final state retains that journal and blocks additional Plex repair, affected updates/recovery and appdata capture until reconciled. A successful normal final-state check clears it. Never delete an operation journal merely to clear an alert: inspect the native process/log and validate database/service outcome first.

Integrity receipts describe the current User Scripts cadence and separately report coverage completeness. Manual Arr failure events are informational historical events; they do not authorize a replacement. Weekly metadata reports keep priority entries while rotating overflow review items. Docker watchdog receipts separate service availability from job review counts; content findings are not silently discarded.

Docker updates with verified differing digests remain `CANDIDATE` while waiting. `--check-only --refresh` requests a bounded full evidence refresh without installation or resetting unchanged candidate stability. `--candidates` shows their observation time, current readiness, holds and next attempt. Short operation locks outside an installation window are not lasting holds. Installation still performs the bounded handoff and fresh safety checks inside the existing windows, with the existing six-Docker/two-plugin rolling limits. No lock or application safety check is bypassed.

Maintain shared code in `tools/operations_contract.sh` and `tools/user_scripts_catalog.sh`, then run their synchronization helpers. Standalone scripts need no runtime library installation. Live descriptions remain user-owned and are preserved byte-for-byte during deployment.

The media mirror now publishes schema-2 per-job completion evidence before shutdown and notification. A later failed attempt cannot replace its last successful receipt. Verification means rsync completed with statistics and final source/lease checks; it does not mean unchanged media was fully rehashed. Earlier log-based successes remain explicitly legacy evidence until a real new transfer completes. `backup_media_remote --evidence-status` is read-only and does not wake ISS.

UI-reachable SABnzbd, Bazarr, Tautulli and PhotoPrism receive bounded native backend probes. Credentials remain inside the existing containers, response bodies are not logged, and unavailable/disabled authentication is reported as unverified configuration rather than a restart instruction. Docker health, maintenance and bounded recovery rules remain active.

RAM checkpoint receipts identify the current boot, archive manifest and compressed size. The hourly audit independently checks this read-back and a one-hour checkpoint age; unchanged verified snapshots remain valid without repeated copying. This metadata check does not rehash compressed payloads. Syslog freshness uses its last successful scan/delivery receipt, current boot and dynamic enabled cadence rather than mere invocation. Both checks allow the first 30 minutes after boot and ignore retired/disabled optional jobs. Existing hourly audit grouping handles attention/reminders; no new timer is installed.

Media health publishes separate current-workflow and historical-event error counts in `health-presentation.json`. Retained history is not silently resolved. Backup deferrals record their start, elapsed time, read-only service coverage and full-monitoring resumption separately; existing issue state is preserved.

The updater and hourly audit compare exact live User Scripts launchers and normalized cron timing against the dynamic catalogue, detecting missing, duplicated, orphaned and mistimed jobs. Discovery continues during drift, but new installations wait for verified timing. No launcher shell text is evaluated and no additional cron entry is created.

## November 26 operational completion

All 18 active scripts clear stale finish/exit/duration values when a new invocation starts, retaining the previous result separately. The hourly audit compares reviewed live code checksums against `user_scripts_status/deployments.json`. Deployment records include private live configuration in the checksum, never its values; descriptions remain user-owned and are excluded. A manual code/configuration edit needs review and registry renewal, not an automatic overwrite.

Media cleanup holds retirement for **30 days**, preserving existing hold start times. Fresh native API, media, monitoring, exemption and pending-work checks still precede removal. Shortening the hold can make an existing 30–89-day candidate eligible on its next normal run. Removed Arr items' dormant state has its separate **90-day** retention. Missing catalog IDs are omitted from expensive entity planning; no filesystem deletion is inferred from API absence. Cancelled holds remove only the native `retirement-pending` tag assignment; shared tag definitions and unrelated tags are retained. Reports distinguish configured-disabled phases, recovery-only phases and historical delivered events. Committed SAB quarantine actions publish exact source-removal receipts for health-warning reconciliation; title similarity alone never resolves a warning.

Appdata retains **one successful generation**, deleting its predecessor only after successful promotion. Docker owners restart after their archive; supported watchdog backend readiness is checked within a bounded startup allowance, with stop-to-readiness elapsed time logged. An unknown service receives explicitly delegated readiness evidence. Restore drills select up to three eligible archives within the existing extraction budget, prioritizing never-tested/old/changed coverage and shorter critical-app coverage targets. Full versus selective Plex restore evidence stays distinct.

Both ISS producers observe bounded network reachability after an accepted shutdown. `offline_observed` is network evidence, not proof of physical power state. A still-reachable remote becomes an attention condition without repeating shutdown or waking ISS. Copy verification remains independent. The hourly audit verifies the latest two managed RAM archive checksums and gzip CRC at most weekly, preserving failed archives for review. Plugin recovery captures only locally available package cache files referenced by the installed definition, within 64 files/256 MiB; missing vendor packages, runtime mutations and database rollback are not guaranteed.

The existing health-monitor handoff uses a bounded **API-only** integrity recovery tick. Heavy inventory/decode/replacement verification stays with the scheduled integrity audit; no extra cron is created. Automatic integrity replacement remains disabled. Schema-2 integrity evidence separates real scans, inventory completion and decode progress from validation/recovery invocations; API polling cannot refresh genuine scan freshness.

Syslog scans resume chronological backlog in bounded 500-line/1 MiB batches with a processing time budget. Rotation/cursor evidence and incomplete final lines retain retry ownership. New messages matching the configured error/storage/critical detectors enter `syslog_watchdog/incidents.json` automatically, with fingerprint, first/last observation, severity, example and attention flag. The ledger is bounded to 2,000 incidents/90 days, spools to RAM if the vault is unavailable and migrates on recovery. It does **not** learn or edit ignore rules. Known critical kernel, storage, filesystem, OOM and coverage conditions bypass ordinary ignores and request an Unraid alert automatically; identical incidents keep the daily reminder limit. A separate bounded critical-tail check prevents an ordinary backlog delaying urgent events. Unknown future wording can be recorded when it matches a detector; semantic criticality cannot be guaranteed for messages no detector recognizes.

DNS stores bounded latency trend samples without introducing a new restart trigger. Torrent category summaries report elapsed time and candidate bytes/files on the console only, reusing the ownership walk. Metadata advice distinguishes known empty/filtered selections from artwork destination failures without suppressing native errors. Live schedules, Docker images/startup/application configuration, and user descriptions are unchanged.

## Backup profiling and queue presentation

`backup_vault_remote` v1.24 records per-attempt source-manifest, rsync-transfer and destination-SHA256 wall times. Totals and up to 128 stage records are embedded in its existing central status receipt under `profiling`; normal completion notifications include the three time totals. Failed/retried stages remain visible. No extra payload pass is added: appdata validates its producer manifest, while other configured sources build payload hashes. Transferred-file bytes and rsync-sent bytes are reported separately from total source size. The effective changed-file MiB/s includes rsync overhead and reuse effects; it is not a measurement of the 2.5 Gb/s physical link. Profiles appear after the next real invocation; no ISS wake is needed merely to deploy profiling.

`media_health_monitor` v3.26 adds queue notification context for packs/multiple targets and import retries. Rows are correlated only by exact download ID; known native episode IDs are listed with a 20-ID display bound. Multiple rows may be duplicate tracking rather than a proven pack. Release-name hints are explicitly unproven and never provide target identity or alter automation eligibility. Retry presentation includes attempts, command/checkpoint/import evidence and the four-hour spacing/action-window gates. Completed native commands remain distinct from successful imports. This changes detail within existing lifecycle/grouped delivery, not notification frequency or mutation rules.

A cleanup warm-run measurement compares repeat processing using already-saved discovery indexes and sidecar fingerprints. OS filesystem caches can also affect time. A preview still updates observation state normally, so a non-mutating benchmark uses copied state and suppressed notification delivery, plus GET-only API transport. Such a shadow preview estimates planner/cache cost; it does not certify execution cost for actual moves or deletions and is excluded from production completion evidence.
