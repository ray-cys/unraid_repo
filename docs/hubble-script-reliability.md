# Hubble script reliability

Scheduled, argument-free executions of the 18 live scripts are supervised by a small parent process. Graceful TERM/INT forwarding is registered before launch; existing producer traps complete before the parent records the final exit. The installed User Scripts Abort button also sends SIGKILL, which cannot run cleanup. Forced aborts and power loss therefore require interruption/journal reconciliation; this supervisor does not modify the plugin or claim forced-abort recovery. CLI commands and library sourcing keep their existing behaviour. Automatic production receipts accept only installed User Scripts paths; fixture/repository executions cannot contaminate live results. RAM and vault execution receipts are separate from producer results: `COMPLETED` means an invocation finished successfully, not that all media was decoded or all backup payloads restored. Overlapping invocations cannot overwrite the active receipt. No new cron entry is installed.

The existing hourly backup audit discovers enabled jobs through the shared User Scripts catalogue. It reports excessively long-running jobs without terminating them and checks completion against the actual cadence, with finish allowances for long jobs and an onboarding interval for new receipts. Missing/retired optional scripts drop out of active checks; history remains retained. Torrent execution findings remain console-only. Existing producer health, backup integrity and restore evidence checks remain independent.

Backup and Plex DBRepair notification failures retain exact subject, importance, summary and detail in a private outbox. The hourly audit retries at most three reports; the original producers also retain their lifecycle semantics. Retried ISS incidents record their exact request/reason acceptance so the existing daily reminder cooldown still applies. Successful delivery is acceptance by Unraid's notification helper, not proof of mailbox delivery. Other scripts retain their own grouped outboxes and daily/weekly limits. An unavailable vault uses a RAM spool; sudden power loss can lose that unpersisted spool. Routine healthy notifications are unchanged.

New appdata archives record GNU tar's already-streamed byte count rather than rewalking appdata. Legacy raw size zero means unknown. Oversized/unknown-size Plex archives receive a selective database/preferences restore; full-archive extraction remains bounded. The ISS default weekly drill is due once per Singapore calendar week during a normal backup session; custom non-weekly intervals retain elapsed-time checks. The coverage ledger explicitly distinguishes that selective test from a complete Plex Media restore. Extraction, hashes and database checks run in isolated staging and never overwrite live data.

The Arr monitor's global backup/update gate still prohibits pipeline actions. During deferral, bounded read-only Sonarr/Radarr ping and SAB version checks publish separate availability evidence, accounting for per-container maintenance. The DNS watchdog uses Pi-hole's own lease rather than suppressing primary checks during unrelated archives. No application setting is changed.

A native DBRepair intent is recorded before execution. Interrupted or unresolved final state retains that journal and blocks additional Plex repair, affected updates/recovery and appdata capture until reconciled. A successful normal final-state check clears it. Never delete an operation journal merely to clear an alert: inspect the native process/log and validate database/service outcome first.

Integrity receipts describe the current User Scripts cadence and separately report coverage completeness. Manual Arr failure events are informational historical events; they do not authorize a replacement. Weekly metadata reports keep priority entries while rotating overflow review items. Docker watchdog receipts separate service availability from job review counts; content findings are not silently discarded.

Docker updates with verified differing digests remain `CANDIDATE` while waiting. `--check-only --refresh` requests a bounded full evidence refresh without installation or resetting unchanged candidate stability. `--candidates` shows their observation time, current readiness, holds and next attempt. Short operation locks outside an installation window are not lasting holds. Installation still performs the bounded handoff and fresh safety checks inside the existing windows, with the existing six-Docker/two-plugin rolling limits. No lock or application safety check is bypassed.

Maintain shared code in `tools/operations_contract.sh` and `tools/user_scripts_catalog.sh`, then run their synchronization helpers. Standalone scripts need no runtime library installation. Live descriptions remain user-owned and are preserved byte-for-byte during deployment.

The media mirror now publishes schema-2 per-job completion evidence before shutdown and notification. A later failed attempt cannot replace its last successful receipt. Verification means rsync completed with statistics and final source/lease checks; it does not mean unchanged media was fully rehashed. Earlier log-based successes remain explicitly legacy evidence until a real new transfer completes. `backup_media_remote --evidence-status` is read-only and does not wake ISS.

UI-reachable SABnzbd, Bazarr, Tautulli and PhotoPrism receive bounded native backend probes. Credentials remain inside the existing containers, response bodies are not logged, and unavailable/disabled authentication is reported as unverified configuration rather than a restart instruction. Docker health, maintenance and bounded recovery rules remain active.

RAM checkpoint receipts identify the current boot, archive manifest and compressed size. The hourly audit independently checks this read-back and a one-hour checkpoint age; unchanged verified snapshots remain valid without repeated copying. This metadata check does not rehash compressed payloads. Syslog freshness uses its last successful scan/delivery receipt, current boot and dynamic enabled cadence rather than mere invocation. Both checks allow the first 30 minutes after boot and ignore retired/disabled optional jobs. Existing hourly audit grouping handles attention/reminders; no new timer is installed.

Media health publishes separate current-workflow and historical-event error counts in `health-presentation.json`. Retained history is not silently resolved. Backup deferrals record their start, elapsed time, read-only service coverage and full-monitoring resumption separately; existing issue state is preserved.

The updater and hourly audit compare exact live User Scripts launchers and normalized cron timing against the dynamic catalogue, detecting missing, duplicated, orphaned and mistimed jobs. Discovery continues during drift, but new installations wait for verified timing. No launcher shell text is evaluated and no additional cron entry is created.

## November 26 operational completion

All 18 active scripts clear stale finish/exit/duration values when a new invocation starts, retaining the previous result separately. The hourly audit compares reviewed live code checksums against `user_scripts_status/deployments.json`. Deployment records include private live configuration in the checksum, never its values; descriptions remain user-owned and are excluded. A manual code/configuration edit needs review and registry renewal, not an automatic overwrite.

Media cleanup holds retirement for **30 days**, preserving existing hold start times. Fresh native API, media, monitoring, exemption and pending-work checks still precede removal. Shortening the hold can make an existing 30–89-day candidate eligible on its next normal run. Removed Arr items' dormant state has its separate **90-day** retention. Missing catalog IDs are omitted from expensive entity planning; no filesystem deletion is inferred from API absence. Lifecycle tags reflect the current stage: confirmed missing media uses `plex-deleted` for movies or `plex-deleted-series`/`plex-deleted-season` for Sonarr; an eligible whole-item hold uses **only** `retirement-pending`. Existing dual-tagged holds converge during normal runs without restarting their timers. Restored media clears obsolete reserved markers; monitoring/exemption cancellation restores the deletion marker while media remains absent. A Sonarr season marker remains while another previously acted-on season is still confirmed wholly missing. Unrelated assignments, shared tag definitions and monitoring settings are preserved during tag-only reconciliation. Bounded lifecycle/retirement audit history remains inside the existing entity state. At the hold deadline, guarded native deletion removes the movie or whole-series **record** with library-file deletion disabled and an import-list exclusion requested; individual seasons are never retired as independent records. Reports distinguish configured-disabled phases, recovery-only phases and historical delivered events. Committed SAB quarantine actions publish exact source-removal receipts for health-warning reconciliation; title similarity alone never resolves a warning.

Appdata retains **one successful generation**, deleting its predecessor only after successful promotion. Docker owners restart after their archive; supported watchdog backend readiness is checked within a bounded startup allowance, with stop-to-readiness elapsed time logged. An unknown service receives explicitly delegated readiness evidence. Restore drills select up to three eligible archives within the existing extraction budget, prioritizing never-tested/old/changed coverage and shorter critical-app coverage targets. Full versus selective Plex restore evidence stays distinct.

Both ISS producers observe bounded network reachability after an accepted shutdown. `offline_observed` is network evidence, not proof of physical power state. A still-reachable remote becomes an attention condition without repeating shutdown or waking ISS. Copy verification remains independent. The hourly audit verifies the latest two managed RAM archive checksums and gzip CRC at most weekly, preserving failed archives for review. Plugin recovery captures only locally available package cache files referenced by the installed definition, within 64 files/256 MiB; missing vendor packages, runtime mutations and database rollback are not guaranteed.

The existing health-monitor handoff uses a bounded **API-only** integrity recovery tick. Heavy inventory/decode/replacement verification stays with the scheduled integrity audit; no extra cron is created. Automatic integrity replacement remains disabled. Schema-2 integrity evidence separates real scans, inventory completion and decode progress from validation/recovery invocations; API polling cannot refresh genuine scan freshness.

Syslog scans resume chronological backlog in bounded 500-line/1 MiB batches with a processing time budget. Rotation/cursor evidence and incomplete final lines retain retry ownership. New messages matching the configured error/storage/critical detectors enter `host_health_watchdog/incidents.json` automatically, with fingerprint, first/last observation, severity, example and attention flag. The ledger is bounded to 2,000 incidents/90 days, spools to RAM if the vault is unavailable and migrates on recovery. It does **not** learn or edit ignore rules. Known critical kernel, storage, filesystem, OOM and coverage conditions bypass ordinary ignores and request an Unraid alert automatically; identical incidents keep the daily reminder limit. A separate bounded critical-tail check prevents an ordinary backlog delaying urgent events. Unknown future wording can be recorded when it matches a detector; semantic criticality cannot be guaranteed for messages no detector recognizes.

DNS stores bounded latency trend samples without introducing a new restart trigger. Torrent category summaries report elapsed time and candidate bytes/files on the console only, reusing the ownership walk. Metadata advice distinguishes known empty/filtered selections from artwork destination failures without suppressing native errors. Live schedules, Docker images/startup/application configuration, and user descriptions are unchanged.

## Backup profiling and queue presentation

`backup_vault_remote` v1.24 records per-attempt source-manifest, rsync-transfer and destination-SHA256 wall times. Totals and up to 128 stage records are embedded in its existing central status receipt under `profiling`; normal completion notifications include the three time totals. Failed/retried stages remain visible. No extra payload pass is added: appdata validates its producer manifest, while other configured sources build payload hashes. Transferred-file bytes and rsync-sent bytes are reported separately from total source size. The effective changed-file MiB/s includes rsync overhead and reuse effects; it is not a measurement of the 2.5 Gb/s physical link. Profiles appear after the next real invocation; no ISS wake is needed merely to deploy profiling.

`media_health_monitor` v3.26 adds queue notification context for packs/multiple targets and import retries. Rows are correlated only by exact download ID; known native episode IDs are listed with a 20-ID display bound. Multiple rows may be duplicate tracking rather than a proven pack. Release-name hints are explicitly unproven and never provide target identity or alter automation eligibility. Retry presentation includes attempts, command/checkpoint/import evidence and the four-hour spacing/action-window gates. Completed native commands remain distinct from successful imports. This changes detail within existing lifecycle/grouped delivery, not notification frequency or mutation rules.

A cleanup warm-run measurement compares repeat processing using already-saved discovery indexes and sidecar fingerprints. OS filesystem caches can also affect time. A preview still updates observation state normally, so a non-mutating benchmark uses copied state and suppressed notification delivery, plus GET-only API transport. Such a shadow preview estimates planner/cache cost; it does not certify execution cost for actual moves or deletions and is excluded from production completion evidence.

## Verified-rejection cleanup and retry exhaustion

Media cleanup v1.9 introduces `MIN_POLICY_REJECTION_AGE_HOURS=6`, with a minimum of six hours, for exact completed SAB jobs carrying a verified monitor rejection. The ordinary `MIN_COMPLETED_AGE_HOURS=336` and 14-day quarantine retention are unchanged. Fast eligibility is not a move authorization: live queues, current target/file identity, single-video accounting, source stability, root/device checks, Mover, action limits and final move proofs still apply. New policy receipts capture the profile/custom-format configuration fingerprint. Cleanup re-fetches that native configuration and blocks disposal if it changed or cannot be verified. Legacy receipts without this fingerprint do not gain accelerated eligibility.

Cleanup owns `media_cleanup/sab/policy-cleanup.json` (latest matched blockers/deferments) and `source-removals.json` (committed move/restore evidence). The monitor reads those files and updates only its own `policy-actions.json`. Correlation requires application, exact download ID, policy start time, target ID and immutable SAB identity; a vanished source is insufficient. The indexed handoff avoids comparing every action against every receipt repeatedly. Recovery exports include both companion files.

Policy actions expose `workflow` and `cleanup` fields. Rejection, replacement-search submission, payload quarantine and successful import are distinct outcomes. A redundant release resolves after verified quarantine. A replacement case resolves after both quarantine acknowledgement and the independently verified compliant import; command completion alone never proves import. Monitor notifications state why the release qualified, actual paths/outcomes, remaining blocker and whether attention is required. Stable waiting does not create a new notification signature every scan; cleanup acknowledgement overdue for 48 hours after rejection produces a specific lifecycle warning. Existing grouped outboxes, limits and delivery retries remain active.

Manual restore intent is recorded before moving the quarantined payload. A restore or interrupted restore invalidates disposal completion and holds automatic re-quarantine for the matching rejection. This preserves operator intent and existing restore journals; acknowledgements do not override that hold.

After three import retries, at least four hours after a completed/failed final command, the monitor reassesses fresh queue reasons without submitting a fourth retry. A newly supported policy reason can enter only the pre-existing guarded rejection workflow. Permission, storage, persistent-lock, mixed/identity and pack/duplicate conditions retain payloads and receive an actionable assessment. Uncertain/running commands remain under their existing reconciliation. One per-download escalation supersedes stale individual retry-failure cards; exact import proof resolves the escalation and reports recovery while preserving native command history. No generic warning, retry count or timeout authorizes media deletion.

## Exact Sonarr pack automation

`media_health_monitor` v3.28 and `media_cleanup` v1.10 implement the pack workflow as one durable job per exact SAB download ID. This extends Sonarr season/multiple-episode handling; Radarr keeps its existing individually proven movie workflow. Titles only select candidates for examination; native series/TVDB/season/episode IDs and a complete exact-download grab history authorize decisions.

1. The monitor inventories the completed download through Python already inside SABnzbd, as user 99:100. It reads filesystem metadata only, not media content or library directories. Sonarr's read-only manual-import preview must map every inventoried video to exact native episodes. Symlinks/hard-linked sources, changing/extra videos, missing mappings, mixed/unknown rejections, mismatched IDs, user deletion history, exempt tags, changed profiles or integrity-recovery holds preserve the payload.
2. Required files can receive a native **Auto** import scan, within the existing three-attempt/four-hour spacing limit. There is no forced import. Every source video must instead be proven redundant against a current acceptable library file, or explicitly below the custom-format minimum for a still-fileless target, before whole-job queue rejection is permitted. A partially importable pack cannot be rejected. Previously imported targets need exact current-file history proof before the remainder can qualify.
3. Two unchanged plans at least four minutes apart, six-hour SAB/queue grace, existing four-hour action windows, current profile signatures, health checks, per-app leases and shared two-actions/run/four-actions/day limits apply. Queue deletion retains the SAB payload and skips native automatic redownload. Exact queue/history read-back is required; blocklisting also requires matching native release/quality/episode IDs. An uncertain DELETE is never replayed. Native targeted `EpisodeSearch` requests cover only the proven missing rejected episode IDs, once per target within the existing seven-day bound. No series/season search is used.
4. Cleanup consumes the frozen verified plan. It rechecks current native identities, profile, active references, physical existing-library proof for redundant files, all remaining source entries, exact source inode/size/timestamps and Mover before per-file quarantine. Each file gets its own existing recoverable quarantine wrapper and receipt; no library file is moved/deleted. Normal quarantine retention/restore owns the result. Unknown metadata/extras remain; only empty directories may be removed. A manual restore holds the entire pack against automatic re-quarantine and further commands.

The private monitor `pack-actions.json` and cleanup `sab/pack-cleanup.json` join the existing operations-state export. One grouped pack card includes per-file dispositions/cleanup destinations, latest native command outcomes and verified replacements; unchanged results do not enqueue another progress mail. Existing warning/reminder delivery remains in force for unresolved blockers. Completion requires committed quarantine evidence for every planned source video and fresh native replacement-file proof on two separate scans for every rejected target. A completed command or download alone is insufficient. Historical failed commands do not keep an exactly resolved pack unhealthy.

Use the existing read-only command to inspect saved pack and command evidence:

```bash
/bin/bash /boot/config/plugins/user.scripts/scripts/media_health_monitor/script --automation-status
```

`ARR_AUTOMATION_ENABLED=false` or `POLICY_AUTOMATION_ENABLED=false` pauses new pack requests; read-only reconciliation continues. No schedule or Docker image/startup/application configuration change is required. Missing SAB Python/access/native preview support holds the source and reports incomplete proof; it does not install anything or fall back to title matching. Two new pack plans and two replacement follow-ups are examined per invocation; inventories are capped at 40 targets, 200 videos, 800 files and 512 directories, with 128 journal jobs/32 MiB. Resolved jobs expire after 90 days; active/uncertain jobs are retained. Limits or unsupported cases require review rather than relaxed disposal.

Maintain the shared sources in `tools/media_pack_{contract,monitor,cleanup}.sh` and `tools/media_pack_inventory.py`, then run `python3 tools/sync_media_pack.py`. Both deployed scripts embed these sources; no additional runtime library is needed.

Read-only review uses the existing commands: `bash SCRIPT --policy-actions` now appends workflow, cleanup status, blocker and original/quarantine paths to the existing columns; `bash SCRIPT --automation-status` includes up to 50 latest retry-exhaustion assessments. Neither command polls applications, sends notifications or submits actions. Email labels distinguish `[PROGRESS]` from `[COMPLETED]` and include matching batch counts; pending replacement searches are not described as completed recovery.


The execution audit reads each receipt into one RAM snapshot before evaluating its
status, PID, boot identity and timestamps. If a worker has just exited while its
supervisor is committing the final receipt, two bounded one-second read-backs
observe completion, failure or a newer invocation before diagnosing interruption.
A worker observed alive is evaluated from that same receipt generation. Persistent
dead-worker/previous-boot records, failed exits and excessive runtimes still report;
no producer status, schedule or execution receipt is rewritten by reconciliation.

## Weekly media-health review and historical attempts

`media_health_monitor` v3.29 prepares a full backlog review on Sunday at 19:00 Asia/Singapore through its existing five-minute User Scripts schedule. A missed run catches up; installation does not generate a retroactive review. The first review after deployment on 26 November is 29 November 2026. Reports include every active error/warning, including acknowledged issues and exhausted reminders, original Ack IDs/reasons, the latest automatic check and next action. Informational history is separated from actionable faults. Repeated application/title/classification groups combine presentation only; exact download/issue IDs and independent lifecycle records remain intact.

Only the latest **two** `weekly-reports/media-health-review-YYYY-MM-DD.txt` files are retained beneath the existing monitor state directory. There are no permanent companion JSON report files. The full report is delivered in numbered parts through the existing bounded grouped outbox; an unusually large report may require multiple notification pages or scheduled runs. Accepted parts are checkpointed individually, undelivered parts resume without regenerating the snapshot, and the next report waits for pending delivery. Healthy empty reviews are suppressed. Receipt acceptance by Unraid remains distinct from mailbox delivery.

A historical requirement can close as `target-satisfied` only when all exact native targets have valid current file records, current allowed quality and custom-format goals, monitoring and external IDs. When upgrades are enabled, native `qualityCutoffNotMet` must be false and the custom-format upgrade cutoff must also be met. Sonarr checks every known series/season/episode/file identity; Radarr checks the exact movie/file. Two positive scans at least four minutes apart, stable native configuration, healthy collectors, no competing queued parent, protected tags or integrity recovery hold are required. This is API database evidence, not a physical readability check. The original attempt remains UNKNOWN: `arrImportedAt` is never invented and no import receipt, payload cleanup authority, search or media mutation is produced. Prior-file evidence also prevents missing-search/pack automation from treating this as permission to undo later intentional deletion.

Identity-free historical review attempts can be administratively archived after **20 days without observed work**, followed by two separate healthy absence observations. Any current exact ID, matching active release, retained SAB history, positive terminal evidence or incomplete collector blocks archival. Attempts with known targets remain under exact-target reconciliation; an unmet known requirement is never age-dismissed. The original ledger, warning and Ack ID are retained under `monitor.historicalReviewArchive` with outcome `UNKNOWN`; notifications explain the reason and state that no import/cancellation was inferred. Positive queue reappearance reopens tracking. Archive evidence is bounded to 180 days and 1,000 entries; undelivered entries are retained and a full archive prevents further archival. This 20-day inactivity threshold is deliberately longer than normal flow/reconciliation windows; separate resolved-issue and ledger retention remain unchanged.

Defaults are `WEEKLY_MEDIA_REVIEW_ENABLED=true`, `WEEKLY_MEDIA_REVIEW_KEEP_REPORTS=2`, `TARGET_SATISFACTION_RECONCILE_ENABLED=true` and `HISTORICAL_REVIEW_ARCHIVE_DAYS=20`. `tools/media_health_review.sh` is the maintained source; run `python3 tools/sync_media_health_review.py` to refresh its embedded standalone copy after changes. Existing acknowledgement, dismissal and automation CLI commands retain their current behaviour. Weekly reporting requires no additional cron entry or Docker/application configuration changes.
