Purpose: Deliver Hubble's completed local backups and configured vault data to independently restorable generations on ISS.

Schedule: 10 * * * * (hourly at minute 10, Singapore time). This is a short completion-request check, not a resident service or an hourly full backup.

appdata_backup publishes a request after successful local completion. No request/already delivered means a local no-op: no ISS connection, Wake-on-LAN, new backup log or notification. A new valid request transfers appdata, flash backup, User Scripts, GitHub directories, photos and compact operational state. Wait for ISS readiness; use the shared backup lease; verify SHA-256 before promoting the remote generation. Retain three successful generations, run a bounded weekly restore drill when due, then request guarded shutdown.

Undelivered requests retry on later checks; invalid/changed/stale requests fail safely. Acknowledged delivery is not repeated merely because later retention/drill/shutdown reports a warning. Photos/GitHub/flash changes alone wait for the next appdata completion request.

CLI: bash script --help or --version performs no backup work. --force repeats the current valid request and may wake ISS/transfer all jobs. GitHub source: user_script/vault_backup.sh; installed entry: vault_remote_backup. Preserve the installed DRY_RUN setting.

Recovery inventory (v1.9): Before waking ISS, privately capture read-only Docker definitions, image digests, networks/volume metadata, compact Docker templates/User Scripts/schedules and a recovery runbook inside operations_state/recovery. The existing transfer verifies and replicates these files. No image pulls or container changes occur. Credentials can be present: keep the bundle private. Coverage identifies configured sources and named-volume gaps; it does not certify external mount contents or application startup.
